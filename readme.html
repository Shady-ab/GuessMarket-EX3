Design decisions

Users and login

  • Login is by user name only – no passwords and no sign-up, as required. Names are trimmed, must not be empty and are at most 40 characters. Any language (including Hebrew) is allowed.
  • A name that belongs to a user who is currently online is rejected (HTTP 409) with a clear message, and the login screen lets the user try another name.
  • A user is "online" while the client keeps polling (last request less than 6 seconds ago). After Logout, closing the window or 6 seconds without requests, the same name can log in again and continues the same account (balance, holdings, ledger). This is the natural behaviour for a system without passwords and without persistence.
  • A new user starts with balance 0 and adds money with Deposit (positive amount, at most 1,000,000,000).
  • If an action makes the balance negative (for example the market maker covers a deficit when closing an event) the user is blocked from trading and opening events. A deposit that brings the balance back to 0 or more unblocks the user automatically.

Events and XML upload

  • The XML is uploaded as multipart/form-data and parsed directly from the request stream in memory. The file content is never saved on the server: the servlet's fileSizeThreshold equals the maximum file size (5 MB), so Tomcat never writes a temporary file, and nothing is kept after parsing. Apache Commons is not used.
  • Validation: everything from EX1 (structure, description, commission 0–90 with type on-close/on-purchase, exactly one market method, LMSR b>0, order book d>0, initial investment ≥ 0, allow-mint true/false), at least two options with unique names (case-insensitive), no duplicate event names inside the file, and no event whose name already exists on the server. A file with any error is rejected as a whole and nothing is added.
  • Events from all uploads accumulate. Each event gets a serial id from the server (the XML has no event id). The uploading user becomes the market maker of all events in the file.
  • The spelling variants comision and inital that appear in the course examples are accepted together with commission and initial.
  • Multi-option events (more than 2 options) are fully supported:
    • LMSR: cost C(q) = b·ln(Σ eqi/b) (computed with log-sum-exp for stability), price of option i = softmax, and the market maker pays the subsidy b·ln(N) when opening.
    • Order book: one book per option with price-time priority; a trade is executed at the resting order's price. With allow-mint, if the incoming bid plus the best bids of all other options reach d, a complete set is minted: the resting bids pay their price and the incoming bid pays the complement max(0, d − sum). The initial investment buys initial / d complete sets for the market maker.
  • Commissions: on-purchase is paid by the buyer on top of the price and goes to the market maker immediately; on-close is taken from the winners' payout when the event is closed. Whatever remains in the event account after closing is returned to the market maker. Every money movement appears as a separate ledger line.

Server

  • One engine instance is stored in the ServletContext. All engine methods are synchronized, so concurrent requests are safe and the JSON snapshots sent to clients are consistent. XML parsing happens before taking the lock, so a large upload does not block other users.
  • All responses are JSON (Gson). Errors are returned as {"error": "..."} with a proper status code (400 invalid input, 401 not logged in, 409 name taken, 500 unexpected), and the client shows the message as is.
  • The logged-in user is kept in the HTTP session (cookie JSESSIONID). No data is persisted – restarting Tomcat starts from scratch, as required.

Client

  • HTTP is done with the JDK java.net.http.HttpClient (asynchronous, with a cookie manager), so the client needs no extra libraries except Gson and JavaFX. Network calls never run on the JavaFX thread.
  • Refresh by pull every 0.5 seconds. Lists that are small (events, users, selected event) are fetched whole and the screen is updated only if the content changed; growing lists (ledger, chat) are fetched as deltas (ledgerFrom / version). A poll is skipped while the previous one is still running.
  • If the server stops or the session expires, the client returns to the login screen with an explanation.
  • The window size is computed from the screen size, and every screen uses resizable layouts (split panes, growing tables). The EX2 components were reused: filters, event table, event details text, trade dialogs and formatting.

Screens

  • Login – user name only; errors (name taken, server not running) are shown on the same screen.
  • Events – all events in the system with filters (type, status, commission, "only my MM events"), details of the selected event (prices, order books, history, participants) and the actions Open / Close (for the market maker) and Participate / Trade. "Load events XML" is in the top bar.
  • My account – name, balance, blocked state, Deposit; my events with my involvement (as in EX2); the ledger, one line per action including commissions received; and all other users with balance and whether they are market makers.
  • Chat (bonus).

Modules and main classes

The project has four modules: GuessMarketEngine (logic, updated from EX2), GuessMarketDto (JSON objects shared by server and client), GuessMarketServer (servlets, packed into the WAR) and GuessMarketClient (new JavaFX client).

Engine (guessmarket.engine)

ClassRole
GuessMarketEngine / GuessMarketEngineImplMulti-user engine: login/logout and online tracking, adding events from an XML stream, deposit, open, buy (LMSR), place order, close. Thread-safe.
EventXmlParser, EventDefinitionNew EX3 parser that reads the XML from an InputStream (no file), validates it and returns event definitions.
MarketEventOne event with N options: LMSR pricing, order books, matching, minting, commissions and closing.
UserBalance, holdings, blocked flag, market-maker events, online time and the ledger. Every credit/debit adds a ledger line.
LedgerEntryOne ledger line: sequence number, time, description, amount, balance after.
OptionOrderBook, BookOrder, TradeRecordOrder book of one option, a resting order and a trade history record (from EX2, extended for N options).

DTO (guessmarket.dto)

ClassRole
ApiContext path, endpoint paths and parameter names – one place shared by server and client.
EventSummaryDto, EventDetailsDto, OptionDto, BookDto, OrderDto, TradeDto, ParticipantDtoEvents list and full event details.
MyUserDto, HoldingDto, LedgerLineDto, UserSummaryDtoMy account (balance, events, ledger delta) and the other users list.
ChatDto, ChatLineDto, MessageDtoChat delta, and the success/error message of every action.
